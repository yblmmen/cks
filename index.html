01 / Cluster lifecycle

Kubernetes 업그레이드와 Projected Volumes

순차 업그레이드와 버전 스큐

마이너 버전은 한 단계씩 순차적으로 올립니다. 예를 들어 1.31 → 1.32 → 1.33 순서입니다. kubeadm 업그레이드는 Control Plane과 Worker Node 모두를 대상으로 합니다.

kubeadm upgrade plan
kubeadm upgrade apply

plan으로 가능한 버전을 확인하고 apply로 적용합니다. kubelet은 apply 과정에서 업그레이드되지 않으므로 별도 수동 업그레이드가 필요합니다.

예시: kube-apiserver 1.32

제공된 버전 스큐 예시에서 controller-manager, scheduler, cloud-controller-manager는 1.32 또는 1.31입니다. kubectl은 1.33·1.32·1.31을 지원합니다.

컴포넌트마다 허용되는 버전 범위를 확인하고 순차 업그레이드 계획을 세웁니다.

Projected volumes

여러 볼륨 소스를 Pod의 단일 마운트 경로로 결합합니다.

SecretconfigMapserviceAccountTokendownwardAPIclusterTrustBundle

핵심 연결

업그레이드는 호환 범위를 고려한 변경 관리이고, Projected volumes는 Pod에서 필요한 설정·자격 증명·메타데이터를 한 마운트로 모으는 방식입니다.

02 / Least privilege

Linux Capabilities

root의 무제한 권한과 일반 사용자의 제한만으로 부족한 경우, 전체 root 권한 대신 필요한 작업 권한을 프로세스에 부여할 수 있습니다.

Capability할 수 있는 작업
CAP_NET_BIND_SERVICE1024 미만 포트에 바인딩
CAP_NET_RAWraw socket 사용. ping은 이 권한만으로 ICMP 패킷 송수신 가능
CAP_SYS_TIME시스템 시각 수정
CAP_SYS_ADMIN여러 관리 작업 수행
CAP_DAC_OVERRIDE파일 권한 검사 우회

포트 900 실습 관점: 비특권 사용자가 실행할 프로그램에 CAP_NET_BIND_SERVICE를 부여하면 동작하게 할 수 있습니다. 부여하지 않으면 permission denied가 발생합니다. 목적에 필요한 권한만 더하는 것이 전체 root 실행보다 제한적입니다.

03 / Pod & container

Security Context와 컨테이너 권한

Security context는 Pod 또는 Container의 권한과 접근 제어 설정입니다. 컨테이너를 root로 실행하면 탈출 상황에서 호스트 파일에 접근할 위험이 커질 수 있습니다. 비-root 실행은 그 위험을 제한하는 한 겹의 방어입니다.

runAsUser · runAsGroup

runAsUser는 프로세스 UID, runAsGroup은 기본 GID를 지정합니다.

fsGroup

볼륨 파일에 적용할 그룹 ID를 지정합니다.

readOnlyRootFilesystem

루트 파일시스템을 읽기 전용으로 마운트해 파일 변조 공격을 줄입니다.

쓰기 공간 분리

임시 쓰기 공간이 필요하면 /tmp 등에 emptyDir를 별도 마운트할 수 있습니다.

로그·캐시·런타임 설정을 루트 파일시스템에 기록하는 앱은 읽기 전용 설정에서 기능 문제가 생길 수 있습니다. 쓰기 경로를 파악하고 필요한 공간만 분리합니다.

04 / Network visibility

Cilium 네트워크 정책

대상 엔터티와 방향·포트 범위를 분명히 해 허용 경로를 좁힙니다.

대상 엔터티를 정하기

world는 클러스터 외부, host는 로컬 노드, remote-node는 다른 클러스터 노드, cluster는 클러스터의 모든 워크로드, all은 내부·외부 전체를 뜻합니다.

Layer 4 범위 적용

포트와 프로토콜 기준으로 송수신을 제한합니다. 별도 Layer 4 정책이 없으면 모든 포트·프로토콜과 ICMP가 허용됩니다. 예시는 TCP 80 outbound 허용과 kplabs.in 도메인 DNS 허용입니다.

Deny 우선순위 이해

Deny 정책은 Allow보다 우선합니다. ingressDeny는 특정 수신 트래픽을, egressDeny는 특정 발신 트래픽을 차단합니다.

관리 트래픽 암호화 확인

Cilium은 관리 대상 호스트·엔드포인트 트래픽에 IPsec 또는 WireGuard 투명 암호화를 지원하며, tcpdump로 확인할 수 있습니다.

05 / Architecture

모놀리식에서 마이크로서비스로

업무 기능을 어떤 경계로 배포하고 확장할지에 따라 운영 부담과 선택지가 달라집니다.

모놀리식마이크로서비스
  • 여러 업무 기능이 하나의 코드베이스와 애플리케이션 서버에 결합
  • 일부 기능의 버그에도 전체 재배포가 필요
  • 한 기능만 확장하기 어려워 자원 낭비 가능
  • 기술 선택이 제한되고 코드베이스 규모가 협업 부담으로 이어질 수 있음
  • 기능별 서비스를 독립 배포·확장
  • 부하가 큰 서비스만 확장 가능

06 / Build & runtime

정적 분석과 Docker 보안

정적 분석으로 설정 검토

프로그램 실행 전에 소스 코드를 검사합니다. Checkov 같은 도구로 다음과 같은 규칙을 점검할 수 있습니다.

  • root로 실행 금지
  • Host Volume Mount 금지
  • HostNetwork 금지
  • ImagePullPolicy != Always

Dockerfile 기본 점검

  • 최신 기반 이미지 사용: 자료 예시 ubuntu:18.04에서 ubuntu:24.10
  • 불필요하면 Alpine 같은 최소 이미지 선택
  • RUN 명령을 결합해 레이어 수 줄이기
  • root 대신 제한 권한 사용자 appuser로 실행

데몬 권한과 원격 노출

Docker daemon은 보통 root 권한으로 실행됩니다. Docker 그룹 사용자도 호스트 root 권한에 준하는 위험이 있습니다. tcp://0.0.0.0:2375 또는 :2376 노출은 원격 공격 표면이 됩니다.

설정과 신뢰 연결

설정은 JSON 파일(선호) 또는 dockerd 플래그로 할 수 있습니다.

Linux: /etc/docker/daemon.json
Windows: C:\ProgramData\docker\config\daemon.json

HTTP 접근이 필요하면 TLS(HTTPS)와 인증서 기반 신뢰 연결을 사용합니다.

08 / Runtime detection

Falco 런타임 탐지

Network Policies와 RBAC가 예방을 돕는다면, 런타임 탐지는 환경의 활동을 관찰하고 이해하는 데 필요합니다. Falco는 조건에 맞을 때 경보를 내는 오픈소스 런타임 보안 도구입니다.

관찰할 수 있는 활동 예

  • 컨테이너 내부 shell 실행
  • /etc/shadow 같은 민감 파일 읽기
  • curl 또는 wget 사용
  • 새 패키지 설치
  • /dev/mem 접근: 물리 메모리에 접근하는 특수 장치 파일로, 무단 접근은 중요 시스템 메모리에 위험을 줄 수 있음

규칙의 기본 요소

  • rules: 고유하고 설명적인 규칙 이름
  • desc: 탐지 위협 설명
  • condition: 경보 조건
  • output: 경보 메시지
  • priority: 심각도. 예: EMERGENCY, ALERT, CRITICAL, ERROR, WARNING

매크로는 반복되는 조건을 재사용하도록 정의한 사전 정의 조건입니다. 자료에는 호스트·컨테이너 이벤트 캡처와 curl 실행 탐지 규칙 예시가 언급됩니다.
